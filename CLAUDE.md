# ConvoyPass: conventions for future sessions

Multi-tenant PWA for approving gate passes for third-party contractor vehicles.
Flow: Driver pre-trip form -> Supervisor approves -> Officer approves -> Security checks in.
**Modules 1 (users, roles, auth), 2 (contractors, vehicles, driver profiles, vehicle QR), 3 (driver scan + pre-trip form, creates `submitted` passes), 4 (supervisor and officer approvals, rejections, revoke) 5 (security gate: scan/search, check-in, deny entry, offline queue) and 6 (dashboard and reports for admin and officer) are built.** Notifications, the audit log viewer and document-expiry alerts come later. There is deliberately **no check-out** (and no weighing, ANPR or multi-day passes): `checked_in` is final.

## Stack
Vite + React 19 + TypeScript (strict, `noUncheckedIndexedAccess`) + Tailwind v4, react-router-dom v7, TanStack Query, react-hook-form + zod, sonner, lucide-react.
Firebase modular SDK: Auth, Firestore, Cloud Functions v2 (Node 22, `functions/`), Hosting, emulators. Path alias `@/` -> `src/`.

## Layout
`src/app` (router, providers) · `src/lib` (firebase, strings, credentials, plate, appUrl, vehicleTypes, errors, api) · `src/features/{auth,admin,vehicles,drivers,qr,supervisor,officer,passes,gate,dashboard,reports,shared}` · `src/components/ui` · `src/types` · `functions/src` · `scripts/{seed,seed-demo,demoHistory}.ts` · `tests/rules`.

## Rules of the road
- **Roles**: `admin | officer | supervisor | driver | security`. Homes: `/admin /officer /supervisor /driver /security`.
- **Tenancy**: every query and write is tenant-scoped (`where('tenantId','==',claims.tenantId)`). Never trust role/tenant/contractor from client input.
- **Claims** `{ role, tenantId, contractorId? }` are set ONLY by Cloud Functions. After a claim change the client calls `getIdToken(true)`. Roles are never stored in localStorage. UI guards are convenience only; Firestore rules + functions enforce access.
- **Firestore rules** are deny-by-default. `users`, `tenants`, `auditLog` have no client writes. `contractors` are admin-writable with field validation, no delete (suspend instead).
- **Auth**: staff = email + password (min 8). Driver = Sri Lankan mobile + 6-digit PIN, signed in via synthetic email `<94XXXXXXXXX>@drivers.convoypass.com` (constant `DRIVER_EMAIL_DOMAIN`; never shown to drivers, never receives mail). `mustChangePassword` forces `/change-password` before anything else.
- **Callables** (`createUser`, `updateUser`, `resetCredential`, `changeOwnPassword`): zod-validated, caller from `request.auth.token` (and re-checked against the caller's active `users` doc), typed `HttpsError` with `details.reason` that the client maps through `strings.apiErrors`. Never log passwords/PINs. Never allow role/tenant changes after creation.
- **Region**: `FUNCTIONS_REGION` (functions/.env) and `VITE_FUNCTIONS_REGION` (.env) must match; default `asia-south1`.
- **Vehicles** (`vehicles/{vehicleId}`): the doc id **is** the permanent QR id, `veh_` + 10 random `[a-z0-9]`, generated server-side, immutable. The QR encodes only `${VITE_APP_BASE_URL}/v/${vehicleId}`, never names or plates. `assignedDriverIds` on the vehicle is the single source of truth for assignments (many drivers per vehicle, many vehicles per driver); a driver's vehicles are derived from it.
- **Plates**: `plateNo` is the display form (uppercase, single spaces), `plateKey` is uppercase alphanumerics only (4-12). Uniqueness per tenant is guarded by `vehiclePlates/{tenantId}_{plateKey}` (`{ vehicleId }`), reserved and moved inside a Firestore transaction. `normalisePlate` is duplicated on purpose in `src/lib/plate.ts` and `functions/src/plate.ts`; so is the vehicle type allow-list (`vehicleTypes.ts`). Change both, plus tests.
- **Drivers** (`drivers/{uid}`, same id as `users`): tenantId, contractorId, name, phone, licenseNo?, photoPath?, status. name/phone/status mirror `users` (written by `createUser`/`updateUser` in one batch; drivers that predate Module 2 are backfilled on their first edit). Photo path is exactly `tenants/{tenantId}/contractors/{contractorId}/drivers/{uid}.jpg`; `updateUser` rejects anything else.
- **Client writes**: none to `vehicles`, `drivers`, `vehiclePlates`. All mutations are callables (`createVehicle`, `updateVehicle`, `setVehicleStatus`, `setVehicleDrivers`, `importVehicles` (<=200 rows, one transaction per row, per-row results), `setContractorStatus`). Contractors keep admin writes for descriptive fields only (name, contactName, phone, address, notes); a new contractor must start `active` and `status` can only change through `setContractorStatus` (admin only; suspend revokes refresh tokens of every user of that contractor, activate touches the doc only). No hard deletes anywhere: suspend instead.
- **Suspended contractors**: `requireActiveCaller` re-checks the caller's contractor on every call (ID tokens outlive revocation), and `AuthProvider` signs out contractor users while their contractor is suspended.
- **Storage rules**: only the driver photo path is open. Write: admin, or the supervisor of that contractor; `image/jpeg`, under 1 MB; create/update only. Read: admin/officer/security of the tenant, that contractor's supervisor, or the driver themselves. A driver cannot read a vehicle they are not assigned to; Module 3 resolves scans through a callable (do not loosen the rules).
- **Lists**: loaded once per scope (`admin` = tenant, `supervisor` = own contractor; supervisors cannot query `contractors` tenant-wide, rules allow only their own doc), max 1000 docs ordered by plateKey/name, filtered client-side, invalidated after mutations. The same feature components serve both scopes via a `scope` prop. Queries must include the same `where` clauses the rules require.
- **QR**: `VITE_APP_BASE_URL` is required for QR screens (`QrGate`); a localhost/private/non-production host (pin the real domain with `VITE_PRODUCTION_HOST`) shows the red "Dev link: do not print" banner. `qrcode.react`, level `Q`; PNG download is 1024 px via canvas. Label sheets print A4 with 10 mm margins (large 90 mm 2x3, small 50 mm 3x5); app chrome hides itself with `print:` variants.
- **Passes** (`passes/{vehicleId}_{dateKey}`): one per vehicle per day. `dateKey` is `YYYYMMDD` in `tenants.timezone` (default `Asia/Colombo`) from `dateKey(timezone, date)` in `src/lib/dates.ts` / `functions/src/dates.ts` (duplicated on purpose; the one place to change for per-trip/per-shift). A non-`rejected` pass blocks everyone else; a `rejected` one is resubmitted in place by the same driver with `attempt + 1` (max 5), the reason moves to `rejectionHistory[]` (with that attempt's checklist and evidence refs). **All writes to `passes` go through callables** (`resolveVehicle` (drivers only, returns a discriminated `state`), `submitPass`, `updateTenantSettings` (admin)); rules give clients read only. Server-side: dateKey, tenant, contractor, plate, driver name and checklist labels are never taken from the client. Evidence lives at `tenants/{tid}/passes/{vehicleId}/{dateKey}/{attempt}/{gps|dashcam|extra1|extra2}.jpg`, is uploaded straight from the browser (driver assigned to the vehicle; only while no pass exists or the pass is rejected and `attempt` is the next one), and `submitPass` re-verifies every file with the Admin SDK (JPEG signature, 10-700 KB, created within 30 min). Earlier attempts' evidence is never overwritten or deleted. Storage rules read Firestore (`firestore.get`): first deploy needs the cross-service IAM grant. Checklist and pass settings come from `tenants/{id}` (`checklist`, `passSettings`) with defaults in `defaultChecklist.ts` (duplicated in `functions/src`).
- **Approvals (Module 4)**: the state machine lives in ONE file, `functions/src/passTransitions.ts`; `src/lib/passTransitions.ts` is a read-only mirror for UI labels (a unit test compares them). Changing the flow means changing the table, the tests and both copies.

  | From | To | Action | Who |
  |---|---|---|---|
  | `submitted` | `supervisor_approved` | approve | supervisor, own contractor |
  | `submitted` | `rejected` | reject | supervisor, own contractor |
  | `supervisor_approved` | `officer_approved` | approve | officer |
  | `supervisor_approved` | `rejected` | reject | officer |
  | `officer_approved` | `rejected` | revoke (`stage: 'revoked'`) | officer or admin, only before `checked_in` |
  | `officer_approved` | `checked_in` | check_in (`stage: 'gate'`) | security only (never admin or officer) |

  - **Admin cannot approve or reject**, at either step, in the UI or the functions (`reviewStageOf('admin')` is `null`). Admin can view everything and revoke.
  - **Expected status and attempt**: every decision carries what the reviewer was looking at (`expectedStatus`, `expectedAttempt`). `decidePass` re-reads the pass inside the transaction and refuses a mismatch with `failed-precondition` / `pass-changed` ("This pass changed. Please review it again."). The UI keeps decisions locked until the reviewer acknowledges a changed pass (`useReviewLock`). `bulkApprove` derives the status from the caller's role and takes only the attempt; `revokePass` takes an optional `expectedAttempt` (the UI always sends it).
  - **Today only**: a pass whose `dateKey` is not today (tenant timezone, same helper as Module 3) can never be approved, rejected or revoked (`pass-expired`). UI status `expired` = waiting for a reviewer from a previous day; read only.
  - **Active checks** (approve and reject, not revoke): the vehicle, its contractor and the driver (`users` doc) must be active, else `vehicle-suspended` / `contractor-suspended` / `driver-inactive`.
  - **Bulk rules**: max 50 items, one transaction per item, per-item `{ passId, ok, error? }`, one failure never fails the batch. A pass with ANY checklist answer `no` returns `has_issues` and is not approved; enforced on the server, and the UI never offers a checkbox for it. A UI selection remembers the attempt that was ticked and drops the pass if the driver resubmits.
  - **Data**: `supervisor` / `officer` `{ uid, name, at }` (cleared on resubmit), `rejection` `{ reason, reasonCode, note?, stage, byUid, byName, byRole, at }` (`reason` = label plus note; for `other` the note alone; Module 3's resubmit screen shows it unchanged), `history[]` of every decision (never trimmed, survives resubmits), `rejectionHistory[]` (earlier rejections with that attempt's checklist and evidence refs). Reasons come from `tenants.rejectionReasons` (2-10, `other` always present, ids are slugs that never change), defaults in `defaultRejectionReasons.ts` (duplicated in `functions/src` and `src/lib`; change both).
  - **Live data**: `usePassQueue` shares one `onSnapshot` listener (limit 100) per distinct query and unsubscribes with the last user; badges (`usePendingCount`) read the same listener as the list. Queries carry the where clauses the rules require (tenant; supervisor also contractor). Indexes: see `firestore.indexes.json`; the emulator does not enforce them, production does.
  - Decisions are optimistic (`useDecisions` hides the decided version, rolls back on error). Callables: `decidePass`, `bulkApprove`, `revokePass`, and `updateTenantSettings` also takes `rejectionReasons`.
- **Gate (Module 5)**: **reads direct, writes via functions.** Security reads `passes`, `vehicles`, `drivers`, `contractors` and driver photos under the existing rules (nothing was loosened); the only writes are the callables `checkIn` and `denyEntry`. `gateEvents/den_{requestId}` (denials, never change the pass) are function-only, readable by admin and officer of the tenant; security, supervisors and drivers have no access. Gates live in `tenants.gates` (`[{ id, name }]`, 1-10, slug ids that never change, default `DEFAULT_GATES` = Main Gate, duplicated in `functions/src/gates.ts` and `src/lib/gates.ts`; deny reasons likewise in `denyReasons.ts`; a unit test compares both copies). `updateTenantSettings` takes `gates`.
  - **Server decides**: today's dateKey, tenant, names, plate, gate name and the check-in time (`checkIn.at` is server time). Everything that blocks entry is enforced in `checkIn` too: status `officer_approved`, `expectedAttempt`, pass is today's, vehicle/driver(`users`)/contractor active, gate exists. Device time is trusted only as the bounded `offlineCapturedAt` (at most 2 min ahead, at most 12 h old; its day in the tenant timezone must equal `pass.dateKey`, so a 23:55 check-in syncs after midnight), stored separately and always labelled unverified.
  - **Idempotency**: every gate call carries a client UUID `requestId` (`newRequestId()`, works without a secure context). Same requestId on a checked-in pass = success with the stored values; a different one = `already-exists` / `pass-checked-in` with `byName`, `at`, `gateName` in `details`. Deny: the doc id is derived from the requestId. Never generate a new requestId for a retry.
  - **Offline queue** (`src/features/gate/offlineQueue.ts`, `idb-keyval`, one queue per guard uid): items hold ids, the plate and the payload only (no names or photos), max 50 (refuse beyond), flushed oldest first one at a time on app start, the `online` event and every 30 s while items wait. No typed `details.reason` (network, `unavailable`, `internal`) = retry later; a typed refusal = `failed` with a readable message, kept until dismissed, plus an amber banner on every security screen. A queued check-in marks the vehicle "Pending sync" so it is not waved through twice.
  - **What the guard sees** comes from ONE pure function, `computeGateResult` (`src/features/gate/gateResult.ts`): not found > already checked in (or pending sync) > vehicle / contractor / driver suspended (beats an approved pass) > no pass today > pass status. Only `approved` offers CHECK IN. `/v/:vehicleId`: security gets actions; admin, officer and supervisor the same view read-only; drivers keep Module 3. `permission-denied` or a missing vehicle = "Unknown QR code"; a denied read of today's pass of a readable vehicle = no pass (rules read `resource.data`). QR text is parsed only by `parseVehicleQr` (`src/lib/vehicleQr.ts`).
  - Firestore uses an in-memory LRU cache (nothing on disk, so one account's data never outlives the page on a shared phone); gate screens preload each other's chunks and prefetch vehicles, today's passes and the people on them, so the gate keeps working through connection drops within a session.
- **Dashboard and reports (Module 6)**: admin and officer only, read only. Supervisors, drivers and security get the 403 page in the UI (`RequireRole`) and `permission-denied` from the functions; nothing new in the rules (admin and officer already read tenant `passes`, `gateEvents`, `vehicles`, `drivers`, `contractors`).
  - **Today is live, history is computed.** `/admin/dashboard` and `/officer/overview` (same `DashboardPage`, `scope` prop) listen with `onSnapshot` to today's passes (tenant timezone, cap 1000, a visible notice at the cap; the shared Module 4 listener store, unsubscribed with the last user) and today's `gateEvents` (cap 200). Tiles, attention panel, contractor table and recent gate activity are pure functions of those snapshots (`features/dashboard/model.ts`). Trends come from the callable `getDashboardTrend({ days: 7|14|30 })`: four `count()` aggregations per day, no documents read, TanStack Query `staleTime` 5 min. Label is always **Checked in today**: there is no check-out, so never say "on site".
  - **SLA**: `tenants.sla { supervisorMinutes, officerMinutes }`, default 30/30 (`defaultSla.ts`, duplicated in `functions/src` and `src/lib`; a unit test compares them), integers 5-240, set by admin through `updateTenantSettings`. A pass is "past SLA" when it waited longer than that at its current step (clock = `submittedAt` for `submitted`, `supervisor.at` for `supervisor_approved`); it leaves the attention panel the moment it is decided. Officers cannot read `users`, so "held by" names the role ("Supervisors of X", "Officers"), not people.
  - **Reports** are the callable `runReport({ type, from, to, contractorId?, vehicleId?, driverId? })`: `gate_log`, `contractor_activity`, `turnaround`, `rejections`, `vehicle_history` (needs `vehicleId`), `driver_history` (needs `driverId`). Dates are `YYYY-MM-DD` in the tenant timezone, inclusive, max **92 days** (`range-too-long`), ids must belong to the tenant (`filter-invalid`). Queries use `dateKey` ranges (gate log: `checkIn.at` and `gateEvents.at` ranges, filters applied in memory). **Scan cap 20,000** passes (check-ins + denials for the gate log): counted first with `count()`, over it the function fails with `resource-exhausted` / `range-too-large` ("narrow the date range"); partial data is never returned. All report logic is pure and lives in `functions/src/reports/*.ts` (plain documents in, `{ columns, rows, summary, generatedAt }` out); `functions/src/reportsApi.ts` does auth, queries and caps only. Report documents are slimmed by the data port (`ReportPass` has no evidence, checklist or capture data), so photo paths and URLs cannot reach a report or an export. Report text (labels, "Check-in"/"Denied", status names) is produced by the server in English; datetimes are epoch ms and formatted by the client in the tenant timezone as `yyyy-MM-dd HH:mm`.
  - **Rules for the numbers**: *turnaround uses the latest attempt only*: `submittedAt` plus the `history` entries whose `attempt === pass.attempt` (stamps are the fallback for passes without history); earlier attempts count only in submissions and rejections. A missing stage excludes the pass from that metric only. p50/p90 are linear-interpolated percentiles (`stats.ts`). *Contractor activity*: submissions = sum of `attempt`; rejections = every `reject` and `revoke` history entry; rate = rejections / submissions; a totals row (`isTotal`) is pinned last. *Rejection data sources*: `rejectionHistory[]` plus the current `rejection` while `status === 'rejected'` (history entries carry no reasons). Rows are ordered deterministically.
  - **Filters live in the URL** (`type`, `preset`, `from`, `to`, `contractor`, `vehicle`, `driver`; `features/reports/filters.ts`). The filter bar edits a draft and only **Apply** writes the URL; the report runs from the URL, so a view is linkable and a refresh repeats it. `?type=gate_log` alone runs today's report (`/admin/gate-log` redirects there). Pass drawers (admin) and the officer review panel link to `vehicle_history` for the vehicle (`vehicleHistoryLink`).
  - **Exports** (`features/reports/exports`): CSV is UTF-8 **with BOM**, CRLF, RFC 4180 quoting; XLSX is built client side with `exceljs` (lazy import) with a "Summary" sheet (report, range, filters, generated time, key figures, breakdown tables) and a "Data" sheet (bold frozen header, widths, real date cells showing tenant wall-clock time). Both contain exactly the rows on screen in screen order. **Formula injection**: any text cell (and header) starting with `=`, `+`, `-`, `@` (or tab/CR) gets a leading `'`. File names `convoypass_<report>_<from>_<to>.<ext>`. **PDF is the print stylesheet** (no PDF library): `@page { size: A4 landscape; margin: 10mm }` is injected while a report is open, chrome is hidden with `print:` variants, the header repeats per page, and `beforeprint` renders every row.
  - Charts are lazy `recharts` inside `ChartPanel`: text description, a "View as table" toggle with the same numbers, pattern fills so meaning never depends on colour. Indexes for passes (tenant + dateKey, + contractor/vehicle/driver, + `checkIn.at`) and `gateEvents` (tenant + `at` asc) are in `firestore.indexes.json`.
- **API payloads**: send phone numbers as typed (`07…`); the server normalises them. The `94…` form is not accepted as input.
- **Strings**: all user-facing text in `src/lib/strings.ts` (Sinhala/Tamil later).
- **Shared logic duplicated on purpose**: `src/lib/credentials.ts` and `functions/src/credentials.ts` (functions deploy from their own folder). Change both, plus tests.
- **UI**: minimalist, slate neutrals, single accent (`accent` tokens in `src/index.css`), no gradients, mobile-first (login, driver, supervisor, security); admin = sidebar on desktop, top bar on mobile. Every list needs loading, empty and error states. Accessible: labels, focus rings, keyboard.
- No `any` (lint-enforced). No secrets, project IDs or credentials in code.

## Commands
`npm run dev` · `npm run build` · `npm run typecheck` · `npm run lint` · `npm test` (unit + component + functions + rules; functions and rules start the Firestore/Storage emulators) · `npm run emulators` · `npm run seed:emulator -- --email … --password …` · `npm run seed:demo` (emulator only; admin, 2 officers, security, 3 supervisors (one contractor suspended), 6 drivers (one disabled, one without a photo), 14 vehicles, two gates, passes in every state and every gate result with fixture photos from `scripts/fixtures/{evidence,drivers}`, 30 days of deterministic history from `scripts/demoHistory.ts` (about 40 passes a day over a 56-vehicle history fleet, ~12% first-attempt rejections, resubmissions, revokes, denials, offline check-ins; `-- --seed=N` or `DEMO_SEED=N`, same seed = same data; history passes have evidence paths but no photo files), prints logins and the gate URLs) · `npm run seed:prod -- --confirm-production --email … --password …`

In a sandbox with an outbound HTTP proxy, run emulator tests with the proxy variables unset (the Storage emulator's Firestore lookups on 127.0.0.1 otherwise go through the proxy and fail).
