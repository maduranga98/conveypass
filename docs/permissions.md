# Permissions matrix

The single source of truth is the `PERMISSIONS` table in `src/lib/permissions.ts`. Cloud Functions deploy from their own folder, so a mirror lives in `functions/src/permissions.ts`; `src/lib/permissions.test.ts` fails if the two differ. Route guards (`rolesFor('area.<role>')`) and `createUser` (`canCreateRole`) read this table. Firestore and Storage rules cannot import it, so they are written to agree with it and are covered by the rules tests.

UI guards are a convenience. Firestore rules and the Cloud Functions enforce access, always scoped to the caller's tenant (called "company" in the UI).

## Roles

| Role | Claim `role` | Sign-in | Scope |
|---|---|---|---|
| Super admin | `platform` (+ `platformAdmin`) | Email + password at `/platform/login` | Platform only, no tenant. Created by script (`npm run superadmin:create`). |
| Company Admin | `admin` | Email + password | Own company. A company can have several. |
| Officer (approvals) | `officer` | Email + password | Own company. |
| Supervisor | `supervisor` | Email + password | Own company and contractor. |
| Safety Officer | `safety` | Email + password | Own company, not tied to a contractor. |
| Security | `security` | 8-digit PIN | Own company. |
| Yard Officer (working name, open item 1 below) | `yard` | 8-digit PIN | Own company, not tied to a contractor. Logs the unloading check only. |
| Driver | `driver` | 8-digit PIN | Own company and contractor. |

PINs are 8 digits, generated by the server, stored only as an HMAC (`pinIndex`) and shown once. See the PIN section of `CLAUDE.md`.

## Vehicle and driver records (expiry tracking)

| Action | Super admin | Admin | Officer | Supervisor | Safety | Security | Driver |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| View vehicles and drivers, with document status | | yes | yes | own contractor | yes | yes | |

Matrix keys: `vehicle.view`, `vehicle.manage`, `driver.view`, `vehicleType.manage`, `expiry.settings`. Enforcement: Firestore rules give clients read access only (no client writes to `vehicles` or `drivers`); every change goes through a callable that checks the caller's role, tenant and, for supervisors, contractor. Drivers read only the vehicles they are assigned to and have no screens here. The Safety Officer can read these records tenant-wide but has no screen for them yet.

Document status (`eligibilityStatus`: `valid`, `expiringSoon`, `expired`) is derived from the expiry dates, today in the company's timezone and the warning window (default 14 days, set in Settings). It is written by the callables when a date changes and refreshed every night at 00:10 (Colombo) by `recomputeEligibility`. A record with no dates counts as valid. Other modules combine it with their own checks; this module does not block passes on it.

## Penalties and suspensions

| Action | Super admin | Admin | Officer | Supervisor | Safety | Security | Driver |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| Issue a penalty (driver, vehicle or both; takes effect at once) | | yes | | | yes | | |
| Revoke a penalty | | yes | | | | | |
| Confirm a penalty was reviewed (add a note) | | | | own contractor | | | |
| View penalties, penalty history, photo evidence | | yes | | own contractor | yes | | |
| Manage the penalty types list | | yes | | | | | |
| View the penalty types list | | yes | | yes | yes | | |
| Run the live eligibility check (`checkEligibility`) | | yes | yes | own contractor | yes | yes | |

Matrix keys: `penalty.view`, `penalty.issue`, `penalty.revoke`, `penalty.verify`, `penaltyType.view`, `penaltyType.manage`, `eligibility.check`. Enforcement: clients only read `penalties` and `penaltyTypes` (Firestore rules: admin and Safety Officer the whole company, a supervisor only their contractor's penalties; officer, security and drivers have no direct access); every change is a callable (`issuePenalty`, `revokePenalty`, `verifyPenalty`, `createPenaltyType`, `updatePenaltyType`, `deletePenaltyType`) that re-checks role, tenant and, for supervisors, contractor. Penalty photos live at `tenants/{tenantId}/penalties/{penaltyId}/evidence.jpg`: written by admin or Safety Officer before the penalty exists (never replaced afterwards), read by admin, Safety Officer and the supervisor of that contractor only.

**A penalty applies immediately.** Supervisor review is a confirmation after the fact (“I have seen this”), never an approval: it does not change whether the penalty blocks. Only an admin revokes. A fixed penalty blocks through the end of its last day (company timezone) and an hourly job then flips it to `expired`; the live check ignores a penalty whose last day has passed even before the job runs.

**Eligibility.** `checkEligibility({ vehicleId?, driverId? })` returns `status` = `blocked` when any active penalty names the vehicle or the driver (a penalty on both applies to each side), otherwise the worst live document status (`expired` > `expiringSoon` > `valid`), plus per-record details. It never returns a penalty's reason, issuer or photo. The gate (`checkIn`) and the vehicle-driver assignment (`setVehicleDrivers`) call the same service, `evaluateEligibility`; the future trip-assignment and gate-scan modules should too.

## Inspections and trip clearance

| Action | Super admin | Admin | Officer | Supervisor | Safety | Security | Driver |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| Record an inspection (approve or reject) | | | | | yes | | |
| Withdraw a standing clearance | | | | | yes | | |
| View inspections and the vehicle's inspection history | | yes (read only) | | own contractor (read only) | yes | | |
| See a vehicle's clearance badge (copy on the vehicle) | | yes | yes | own contractor | yes | yes | assigned vehicles |
| Run the live check that includes clearance (`checkEligibility`) | | yes | yes | own contractor | yes | yes | |

Matrix keys: `inspection.view`, `inspection.record`, `inspection.withdraw`. Enforcement: clients only read `inspections` (Firestore rules: admin and Safety Officer the whole company, a supervisor only their contractor's; officer, security and drivers have no direct access); every change is a callable (`recordInspection`, `withdrawClearance`) or one of the three triggers below. The admin cannot create inspections: inspection authority sits with the Safety Officer only.

**One approval covers every trip.** A vehicle is *cleared* when its current inspection is `active` and `approved`. Records are never edited: a new inspection supersedes the current one (`superseded`), including a rejection, which leaves the vehicle *Inspection rejected* until the next approval. Exactly one record per vehicle is current; `vehicles.clearance` is a copy of it (status, reason, `inspectionId`, time) written in the same transaction, so lists read one document.

**Cancellation (`invalidated`) is event driven, by Firestore triggers**, not by editing the penalty or eligibility code:

| Event | Trigger | Effect |
|---|---|---|
| A penalty is created against a vehicle | `invalidateInspectionOnPenalty` | that vehicle's approval is cancelled, reason `penalty_issued` |
| A penalty is created against a driver | same | the approval of **every vehicle the driver is assigned to** is cancelled |
| A vehicle's `eligibilityStatus` becomes `expired` (daily job or a callable saving an expired date) | `invalidateInspectionOnVehicleExpiry` | reason `document_expired` |
| A driver's `eligibilityStatus` becomes `expired` (licence) | `invalidateInspectionOnDriverExpiry` | the approval of every vehicle the driver is assigned to, reason `document_expired` |
| The Safety Officer withdraws a clearance | `withdrawClearance` (callable) | reason `manual`, with a required note |

Triggers retry and may arrive late, so they only cancel an approval that was recorded **before** the event and re-check that the cause still holds (the document is still expired). A repeated delivery changes nothing. The audit entry is written with `actorRole: 'system'`. There is no time or trip-count interval: correcting the problem and a new inspection are the only way back to *cleared*.

**Combined eligibility.** `checkEligibility` now also returns `inspection` (`status`, `cleared`, `reason`, `at`; never the officer or notes) and `eligible`: documents not expired AND no active penalty AND (when a vehicle is asked about) an active approved inspection. The check reads the inspection record itself, not the copy on the vehicle. `checkIn` does not require clearance yet; the gate-scan module should read `eligible`.

## Visit lifecycle (check-in, unloading check, check-out)

One `visits/{vis_…}` record per vehicle visit with three timestamped stages. Clients only **read** visits; every write is a callable (`checkInVisit`, `checkOutVisit`, `logUnloadingCheck`) or the scheduled dwell job. Eligibility is **consumed** from the shared `checkEligibility` service (documents, penalties, inspection clearance), never decided here.

| Action | Admin | Officer | Supervisor | Safety | Security | Yard Officer | Driver |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| Check a vehicle in (scan, driver PIN, eligibility) | | | | | yes | | |
| Check a vehicle out | | | | | yes | | |
| Log or correct the unloading check (only while the vehicle is on site) | | | | | | yes | |
| Read visits | all | all | own contractor | all | all | on-site visits only | |
| Daily summary (counts, filtered by role) | all tiles | all tiles | own contractor | check-ins, suspensions, long stays | check-ins, check-outs, on site, long stays | unloads, waiting, on site, long stays | |
| Visit timeline page, vehicle and driver history | yes | | own contractor | | | | |

- **Driver duty lock.** `drivers/{uid}.driverOnDutyLock` (+ `activeVisitId`) is set in the same transaction that creates the visit and cleared by the check-out of that visit. A second check-in for a locked driver is refused on the server (`driver-on-duty`), and a vehicle already on site is refused too (`vehicle-on-site`). A driver that predates Module 2 gets a `drivers` doc created from the `users` record. Only the visit functions write the lock (rules: no client writes to `drivers`).
- **Driver PIN at the gate.** The driver types their own PIN on the guard's phone. The server finds them through `pinIndex` (HMAC), checks tenant, role, status and that the driver is assigned to the vehicle, and answers every failure with the same `pin-invalid`. Failures are counted per guard (8 per 15 minutes, then `pin-throttled`); a right PIN is never counted. The PIN is never stored, logged, audited or returned. Check-in needs the internet (there is no offline queue for visits).
- **Order of checks.** Scan, then the PIN (it is what identifies the driver), then `checkEligibility(vehicleId, driverId)`. Eligible: visit created, driver locked. Not eligible: nothing is written except a `visit.checkInBlocked` audit entry, and the response carries the eligibility output unchanged; the screen words it (`deniedReasons`) without re-deriving anything. A suspended vehicle, contractor or driver is refused with its own typed error.
- **Check-out** needs no eligibility, and does not require an unloading check (the screen warns, the server never blocks). It is idempotent per `requestId`.
- **Unloading check** is `unloadingCheck { performed, timestamp, officerUserId, officerName, unloaded, unloadLocation }`. "Unloaded: yes" needs a place (2-60 characters), "no" stores none. It can be corrected while the vehicle is on site; every change is audited.
- **Yard Officer access.** The role reads `visits` with `status == checked_in` and nothing else (no vehicles, drivers, penalties, inspections, passes, settings). Plate and driver name are copied onto the visit at check-in so no other collection is needed. It signs in with a PIN (16-hour session, like Security), gets no push and no notifications settings, and cannot be given a password.
- **Dwell warning.** `tenants.dwellLimitHours` (1-72, default 16, admin via `updateTenantSettings`, Settings > Long stay warning). `flagDwellVisits` runs every 15 minutes and sets `dwellWarning: true` (+ `dwellWarningAt`) on visits still `checked_in` for that long, measured from `checkIn.timestamp`, with a `system` audit entry. It is a **warning only**: the daily summary shows it, nothing is blocked, and no function reads the flag.

### Open items for client sign-off

1. **"Yard Officer" is a working name.** It is the literal label shown in the UI (`strings.roles.yard`, `strings.visits.yard.role`) and the internal role id is `yard`. Rename in those two places if the client prefers another word.
2. **What happens at the dwell limit.** Today: flag and show only. The client still has to choose auto-flag only, hard block, or admin alert, and whether the clock runs strictly from check-in. The limit itself is a company setting, so changing it is one value; changing the behaviour is a change in `flagDwellVisits` and the actions that should read the flag.
3. **Two check-ins at the gate.** The existing pass-based `checkIn` (Module 5: officer-approved pass, `checked_in` is final) and the new visit check-in are separate. Visits do not require a pass and passes do not create visits. Decide whether the visit check-in replaces the pass check-in, requires an approved pass, or both stay.
4. **Driver PIN on the guard's phone.** The driver's sign-in PIN is typed on a device that is not theirs. The guard could shoulder-surf it and sign in as the driver. Keys are masked and failures are throttled, but if this matters, replace it with a one-time check-in code the driver generates in their own app.
5. **`checkIn` does not read `eligible` yet.** It still checks documents/penalties only, as before; the new visit check-in uses the combined `eligible` (including inspection clearance).

## Later modules

Violations beyond penalties, compliance document rules, the Supervisor's trip assignment, gate pass issuance and the month-end qualification list are not built. When they are, add their actions to `PERMISSIONS` (both copies) and this document, instead of adding role checks elsewhere.
